### Soak 3: harness faults found and fixed

Soak 3 ran 320 rounds of each scenario, at the production intervals, from 19:14 to 20:47. It reported 5 PASS / 5 FAIL. Every failure came from the harness. None came from the control plane.

1. **API keys expired.** The tenant API keys made in M06x setup had a fixed 1 h lifetime. They expired at tag round 318, and from then on every call got 401. That is correct behaviour for an expired key. M06x.a–d and the undo step therefore failed. **Fix:** the lifetime is now 1 h plus one minute per round.
2. **A change seen after the bound still counted as met.** The harness poll checked the 10 s bound only after a poll that did *not* see the change. Each poll is two new ssh connections from the operator laptop, which was off the lab LAN and reached it through a Tailscale subnet route. When one poll stalled for tens of seconds, a change it then saw still counted as met. Out of 634 tag changes, 40 were recorded above 10 s, with a maximum of 47.8 s. Soak 2, run earlier on the same binary, recorded none above 3.8 s. **Fix:** a value above the bound is now a miss, whichever way the wait ended.
3. **The soak verdict did not depend on M06x.a–d.** `M06x.soak` reported PASS on divergence alone, and its message said "every change <= 10s". **Fix:** the verdict now needs all four of M06x.a–d to pass. Otherwise it fails and divergence is not judged.

**The slow values came from the ssh polls, not from propagation.** a1's tailscaled logs `wgengine: Reconfig` when its peer set changes. Matching each tag API call to the next reconfig on a1 gives, to the second: p50 0 s, p90 0 s, p99 6 s. Two examples:
- The slowest round (tag-on 317, 47.8 s in the harness): the API call returned at 13:23:34 and a1 reconfigured at 13:23:34.
- Tag-off 112 (23.7 s in the harness): API 12:44:14, a1 12:44:14.

tailscaled rate-limits this log line, so this check is only indicative for rounds where lines were dropped. It is not proof for those rounds.

Divergence over soak 3 was **0** across 144 reconciles on the active process. The 317 completed tag rounds ran with no divergence.

**Measurement change (`m06x-watch.py`).** The time is now taken on a1 itself:
- One ssh session runs a watcher that polls the local `tailscale status --json` every 0.1 s.
- The harness sends `MARK` right after each API call returns.
- The reported time is the time on a1 from receiving `MARK` until the change is visible, plus the measured harness→a1 round trip of the `MARK` line. That sum is an upper bound of "API returned → visible at a1".
- An ssh stall between the operator machine and the lab now delays the harness but does not change the measured value.
- `M06X_WATCH=0` keeps the old harness-side poll, now with the bound fixed.
